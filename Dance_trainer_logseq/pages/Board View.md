- **`TaskCard`'s description preview renders through the shared `MarkdownNote` component now**, in its read-only mode (`:editable="false"`) — one cheap single-pass parse per card, no block-editing machinery. The truncated-preview sizing, dim ink and dead-link treatment are `TaskCard`'s own CSS, themed onto the shared component via `--note-*` custom properties. See [[Card Notes]] for the component itself; this page doesn't otherwise cover the description field.
- ## Two drag systems, not one
	- **Mouse uses native HTML5 DnD; touch is hand-rolled from pointer events.** Not a stylistic choice: touch has no HTML5 drag at all in mobile browsers, and the moment you take `setPointerCapture` (needed to keep receiving moves once the finger leaves the card) `dragover`/`drop` stop firing on the elements under the finger. So the touch path can't learn what it's over from events and has to hit-test geometry instead. Every duplicated concept below (`dropIndicator` vs `touchDropIndicator`, `onCardDragEndTouch` vs `onColumnDrop`) exists because of that split, not by accident.
	- **`draggable` is switched off per-pointer, on `pointerdown`.** `nativeDraggable` in `TaskCard.vue` (and `nativeColumnDraggable` in `KanbanColumn.vue`) is set to `e.pointerType !== 'touch'` before anything else happens. Android Chrome starts a *native* touch drag on long-press over a `draggable` element, racing the custom one; the native drag can't proceed (the touch-scroll guard and pointer capture disrupt it) so the browser aborts it with an immediate `dragend`, which bubbled to `onBoardDragEnd` and cleared `dragState` — the visible symptom was the quick-move buckets appearing and vanishing in the same gesture (commit `f50875b`).
		- `onBoardDragEnd` keeps a second guard for the same failure: `if (touchPoint.value) return`. Touch drags are torn down on `pointerup`, never on `dragend`, so any `dragend` arriving mid-touch-drag is by definition stray.
	- **Touch drag starts on a 350 ms long press (`LONG_PRESS_MS`), cancelled by >10 px of movement (`MOVE_CANCEL_PX`).** The card has no drag handle, so the press is the only thing separating "drag" from "tap to open" and from "swipe the board sideways". The column's `⠿` handle uses a shorter 300 ms (`HANDLE_LONG_PRESS_MS`) because there the target is unambiguous. Contrast [[Practice Companion View]], where the `⠿` grip lifts with no wait at all.
	- **Scrolling is blocked by a non-passive `touchmove` listener, not by `preventDefault` on `pointermove`.** `preventDefault` on a pointer event does not stop native scrolling; only `blockTouchScroll` registered `{ passive: false }` does. It is attached only once the drag is live — by then the finger has been still for the long press, so no scroll momentum exists to fight. The card keeps `touch-action: pan-x pan-y` precisely so a plain swipe still scrolls the board and the column.
	- **A drag must not also open the card.** Both `dragend` and the touch `pointerup` set `suppressNextClick` and clear it on the next `requestAnimationFrame` — browsers fire a synthetic click on the drag source right after a drag, and one rAF is long enough to swallow exactly that one.
- ## Hit testing, and what it assumes about the layout
	- **The dragged card is never removed from the DOM.** `.task-card.dragging` is `opacity: 0.4` and nothing else. Every drop index is computed from live `getBoundingClientRect()`, so optimistically pulling the card out of its column mid-drag would reflow everything below it under a stationary finger and make every subsequent measurement describe a layout the user isn't looking at. The card is instead filtered out by id (`excludeCardId` in `resolveCardDrop`).
	- **`resolveCardDrop()` scans a column's cards by vertical midpoint rather than hit-testing the drop point.** The original touch drop was a single `elementFromPoint` → `.closest('.task-card')`, so a finger landing in the 8 px gap between cards, on the composer, or on column padding resolved to nothing and fell through to "append at the end". Since a touch drop gets exactly one point at `pointerup` — no per-card `dragover` to correct it — that read as *mobile drag always drops at the bottom* (commit `ba4917a`). The midpoint scan covers the whole column height, so any `y` resolves to a slot.
	- **The insertion line is one visual with two sources.** `KanbanColumn`'s `effectiveDropIndicator` is `dropIndicator ?? touchDropIndicator` — its own from native `dragover`, or the geometrically resolved one BoardView pushes down as a prop. Mouse users had the feedback from the start; the touch line was added with the midpoint scan, because a one-shot drop with no preview is a guess.
	- **`.drag-ghost` must stay `pointer-events: none`.** It is `position: fixed` under the finger; without that rule every `elementFromPoint` call during a touch drag would return the ghost and no drop would ever resolve.
	- **Data attributes are the hit-test contract.** `data-column-id`, `data-card-id` and `data-quick-column-id` are read straight off the DOM by `columnIdAtPoint`, `resolveCardDrop` and `quickColumnIdAtPoint`. They aren't decorative — removing one silently breaks drops on that surface only in the touch path, which is the path with no test coverage.
- ## Edge auto-scroll
	- Shared by the touch path, the mouse path and column dragging (`startAutoScroll`/`autoScrollLoop`/`stopAutoScroll`), because a board wider than the viewport otherwise can't be crossed in one gesture.
	- **The loop retains the last pointer x rather than reacting to events.** Native `dragover` stops firing when the cursor holds still, so an event-driven scroll stalls exactly when the user is parked at the edge waiting for the board to move. `EDGE` is a 72 px band and speed ramps 0 → `MAX_SCROLL_SPEED` (26 px/frame) with depth into it — a constant crawl read as unresponsive (commit `7483cf3`, which also extended it from touch-only to mouse).
	- **Scrolling invalidates the hit test even when nothing moves.** The loop re-resolves `touchOverColumnId` and `columnDropIndex` on every frame it actually scrolls, since the columns slide under a stationary finger.
	- **`scroll-snap-type: x mandatory` is disabled while dragging** via `.board.touch-dragging`. Snap and a per-frame `scrollLeft` write fight each other; the mobile one-column-per-swipe snap is worth keeping for browsing, not during a drag.
	- Mouse users also get click-drag panning of the board background (`onBoardPointerDown`, guarded to `pointerType === 'mouse'` and `e.target === el`) and vertical-wheel-to-horizontal-scroll, both explicitly stepping aside when the pointer is over a column so a column's own card list keeps scrolling.
- ## Mobile column snapping — and why swipe distance feels random
	- Under 640px the board is a snap carousel: `.board` carries `scroll-snap-type: x mandatory` and `scroll-padding-left: 12px`, `.kanban-column` carries `scroll-snap-align: start` at `min(84vw, 340px)` wide. With the 12px gap that is a uniform 352px pitch — every column is the same width regardless of how many cards it holds, so nothing about the geometry varies.
	- **A swipe does not move one column, despite what the CSS comment beside those rules says.** `scroll-snap-stop` is unset, so it defaults to `normal`, which explicitly permits a fling to cross any number of snap points. What actually happens on `touchend`: the browser measures release velocity, runs it through the platform fling-decay curve to predict where the scroll would coast to, picks the snap point *nearest that prediction*, and animates there.
	- **The felt inconsistency is inherent to that pipeline, not a misconfiguration.** Distance is roughly linear in release velocity, and a thumb flick repeated as identically as a human can manage still varies ±20–30% — which at fling speeds exceeds the 352px pitch. So the nearest-snap-point quantizer returns different columns for flicks that feel the same, and the spread widens the harder you flick. "Sometimes it flies way past, sometimes it moves one" is that quantizer, sampled twice.
	- **CSS exposes no strength dial, and this is a fact about the spec rather than a setting we haven't found.** `scroll-snap-type` is an enum whose strongest value, `mandatory`, is already in use; `scroll-snap-stop` is binary; `scroll-padding`/`scroll-margin` only relocate snap points. The decay curve, the landing prediction, the nearest-point choice and the animation duration are all internal to the compositor. There are exactly three rungs available — today's behaviour, `scroll-snap-stop: always`, or owning the fling in JS — with no ramp between them.
	- **Decided against `scroll-snap-stop: always` (2026-07-26).** It would remove the inconsistency completely and cost nothing but one line, because it forbids a fling from crossing more than one snap point — every gesture then lands exactly one column over, hard or soft. Rejected because the fling is worth more: `JuKi practise` has 14 columns and `Test board` 13, so a guaranteed one-per-swipe means 13 deliberate swipes to cross the board that is actually used.
	- The remaining option, a JS velocity handler that keeps the fling *and* makes it repeatable, is deferred — see [[Open Work]].
	- Separately, `scroll-snap-type: x mandatory` is switched off while dragging via `.board.touch-dragging`; see Edge auto-scroll above.
- ## The quick-move drop bar
	- A strip of the board's `is_quick_target` columns (see [[Tables]]) that slides in over the top of the board while a card is dragged; dropping on one moves the card to that column's end. The card's own source column is filtered out — dropping a card back where it came from isn't a quick move.
	- **The bar is always mounted and toggled by a class, never `v-if`.** Inserting a DOM node during `dragstart` makes Chrome cancel the native drag outright: it fired an immediate `dragend`, which cleared `dragState`, which hid the bar again (commit `376d74f`). It is `pointer-events: none` while inactive so it doesn't eat clicks on the board behind it.
	- The bar overlays the top strip of the board, so a point over a bucket is deliberately *not* inside any column — `onCardDragMove` resolves the bucket first and `onCardDragEndTouch` checks `[data-quick-column-id]` before falling back to column/card resolution.
	- Same mechanic, tap instead of drag, is reused by Session Review in [[Practice Companion View]] and by the card modal — all three end in `store.moveCard(card, column, cardsByColumn(column).length)`.
- ## Column drag
	- Deliberately modelled on the card drag (mouse via native DnD from the `⠿` handle, touch via the handle's own long press) so there is one set of behaviours to reason about, and it reuses the same edge auto-scroll.
	- **`onBoardDragOver` has to `preventDefault()` for columns but not for cards.** A card is always dropped over a column or a card, both of which already call it; a column can legitimately be dropped past the last one onto empty board background, which is only a valid drop target if the board element itself opts in.
	- **`columnDropIndex` and `moveColumnTo`'s argument are different coordinate systems.** The index is a slot in the *full* column list, because the `.column-drop-line` marker is rendered inside the same `v-for`; `moveColumnTo` splices into a list with the dragged column already removed. `finishColumnDrop` subtracts one when the target is past the dragged column's own index. Getting this wrong is a silent off-by-one only visible when dragging rightwards.
	- `KanbanColumn` suppresses its card-drop highlight while `columnDragActive` — otherwise reordering columns lights up every column as if it were about to receive a card.
	- **A `dragenter`/`dragleave` counter can get stuck.** An aborted native drag (Escape, dropped outside the window) fires `dragend` with no matching `dragleave`, leaving `dragOverCount` above zero and the column outlined indefinitely. Every column listens on `document` for `dragend` and zeroes it (commit `8255a64`).
- ## Persistence model (`boardStore.ts`)
	- **Optimistic first, always.** Every action mutates `cards`/`columns`/`labels` locally, then writes to [[Supabase]], then reverts on error and raises a toast. Waiting for the round trip before moving a card would put a ~100 ms lag inside a drag, which is the one place it is unmissable.
	- **Reverting is the whole reason the writes are structured the way they are.** `moveCard` and `sweepDueCards` snapshot *every card in every affected column* — id, column, position, and the three scheduling fields — before touching anything, because a move renumbers cards that the user never dragged. Restoring only the dragged card would leave the rest of the column holding positions that describe a state that no longer exists. Before commit `8255a64` there was no revert at all: a failed write left local state silently diverged from the DB until reload.
	- **`queueCardWrite(cardId, task)` serializes writes per card.** A chain of promises keyed by card id, with `prior.then(task, task)` so a rejected earlier write doesn't strand the queue. The failure it prevents: two fast actions on the same card (double drag, rapid label toggle) issuing overlapping `UPDATE`s whose completion order is not their issue order, leaving the DB holding the earlier state.
		- **The queue serializes ordering, not payloads.** The task reads `c.position` at *execution* time, not at call time, so a write issued for move #1 persists whatever move #2 already put in local state. That converges to the right answer rather than replaying stale values — but it means the queue is not a transaction log, and reasoning about it as one will mislead.
		- **It is keyed on the dragged card, while the write touches the whole column.** Two rapid moves of *different* cards in the same column land in different queues and can interleave. They still converge, for the same reason as above (both write live positions), but nothing enforces it.
		- `updateCardField` (name / description / due date, see [[Card Notes]]) and `sweepDueCards` do **not** go through the queue.
	- **Position arithmetic assumes a full renumber, and ties are broken by array order.** `moveCard` sets `card.position = targetPosition` and then reindexes the whole target column `0..n-1` via `cardsByColumn`. That sort is `a.position - b.position` over a filtered copy of `cards.value`, so the moved card and the card already holding `targetPosition` tie, and JS's stable sort resolves the tie by their order in `cards.value` — which is the order rows came back from the initial `select … order('position')`, not anything the drag knows about. **This is suspected to be a live off-by-one on upward same-column drops** — see [[Open Work]], where it is recorded as unconfirmed.
	- **Positions are dense integers, not gaps or fractions.** Nothing anywhere reserves space between cards, so every move rewrites one `UPDATE` per card in both columns. Fine at this board's size; it is the reason a single move is several requests.
- ## Column rules on move — the Leitner mechanics the board triggers
	- **`moveCard` is where the schedule changes.** Entering a column with `due_offset_days` stamps `due_date = today + offset` (always overwriting) and records `last_scheduled_column_id` / `last_practiced_on`; a column with `due_clear_on_enter` nulls the due date instead. See [[Tables]] for the fields and [[Practice Companion View]] for why the history is stored rather than derived.
	- **Same-column reorders never fire a rule** (`oldColumnId !== targetColumnId`), so dragging a card up its own column to prioritise it doesn't quietly reschedule it.
	- **The history fields are written only for the offset rule, never for `due_clear_on_enter`.** Clearing a due date means "no longer scheduled" — the opposite of a scheduling event — and recording it would make Review show a rung the card was never on.
	- **`sweepDueCards()` moves cards without going through `moveCard` at all**, which is what makes it safe: it must not fire on-enter rules (the due column's own rule would re-stamp everything it collects) and must not touch due dates. Swept cards land on *top* of the due column, most overdue first; it runs on mount and again on `visibilitychange`, because an installed PWA can be backgrounded across midnight and come back with a stale board.
	- `dueColumn` falls back to the leftmost column when no column carries `is_due_column`, so a board that has never been configured still sweeps somewhere sensible.
- ## The card face and the family icon
	- `TaskCard.vue` is presentational — it takes `ancestors` and `partCount` as props and derives nothing. `BoardView.vue` computes both from [[Card Relationships]]'s `lib/cardTree.ts` and passes them down through `KanbanColumn.vue`, which only forwards. The tree walk needs *all* the board's cards (a parent can sit in another column), which is why it happens at the view and not in the column.
	- **The ancestor line sits above the title**, dim and 11 px, so a part is identifiable in a column without its name having to carry its parent's — names are stored leaf-only. It head-truncates via the same `direction: rtl` trick as the note's link chips, because the nearest parent is the informative end (`… › Prep`, not `One Footed …`). No trailing `›` is rendered: it's a bidi-neutral and an RTL paragraph would reorder a trailing one to the far side.
	- **The family icon in the meta row is the only tappable thing on the card face.** Everything else, link chips included, is deliberately inert so a tap anywhere opens the card. This opts out because jumping to the family is the point of showing the count at all. It carries `@click.stop` and `@pointerdown.stop` — the latter keeps it out of the long-press drag arming, so a press on the icon never starts a card drag and `suppressNextClick` never sees the tap.
	- The glyph reads at 12 px to sit level with the due text, far under a thumb target, so a `::after` with negative insets gives it a ~40 px box without the padding making the meta row taller. It overlaps the note above it, which is harmless — a tap there opens the same card, just not at the family.
	- It opens **the card's own modal, scrolled to its Family section**, rather than a popover or an inline expansion. A floating layer would be anchored to a board that scrolls horizontally under it, and expanding the card inline changes its height while the touch drag hit-tests card rectangles.
- ## The app shell never scrolls
	- **`html`, `body` and `#app` are all `overflow: hidden`**, with `html` at an explicit `100dvh`. Every view owns its own scrolling; the document owns none. `#app` is a flex column, and each route lays itself out inside it.
	- **Why it has to be a clip and not a height.** On Chrome for Android the **initial containing block is the large viewport** — the height with the URL bar retracted — fixed at layout time, and nothing in CSS shrinks it. So `body { min-height: 100dvh }` correctly sized the body to the visible ~730px while `<html>` stayed the ICB's ~780px, and the document scrolled by exactly the URL bar's height. That is how the topbar could be dragged off screen **on every route**, board select included. `min-height` on a child cannot shorten its parent's containing block; only clipping the overflow ends it. Desktop never reproduced it because there `lvh == dvh`, so the slack is zero.
	- `height` on `html` must be a viewport unit, not `100%` — `100%` resolves against that same large ICB and reintroduces the gap. The `100vh` line above it is the fallback for browsers without `dvh`, where the two are equal anyway.
	- **Consequence for any new view:** a route that needs to scroll must say so. `.board-view` is `flex: 1; min-height: 0` and scrolls internally; `BoardSelectView` is a *fragment* (topbar + `<main>`), so its `.boards` carries `flex: 1; min-height: 0; overflow-y: auto` and the bar carries `flex-shrink: 0`; `LoginView`'s `.auth` does the same. Forgetting it means content is clipped, not scrolled.
- ## Labels
	- **One control, both palettes.** `LabelBar.vue` (the chips plus a `+`) and `LabelPicker.vue` (the overlay it opens) serve the card modal *and* the practice focus card / Session Review head. The picker takes its colours from the host through a `--lp-*` contract — `--lp-surface`, `--lp-field-bg`, `--lp-border`, `--lp-ink`, `--lp-ink-dim`, `--lp-accent`, `--lp-scrim` — defaulting to the light board, with the dark mapping declared once on `.practice-view` in `tokens.css`. Same no-props pattern as `MarkdownNote`'s `--note-*`: custom properties inherit down the DOM, so even a `position: fixed` overlay picks up the palette of the surface that opened it without being told.
	- **The panel is a checkbox list of *every* label, not a list of addable ones.** The modal used to carry an inline popover that only offered labels the card didn't have, which made *removing* one a separate chip-sized `×` on the chip itself — two controls, two shapes, one job. One panel now adds and removes, and mid-practice that matters more, since a mislabelled card is noticed while looking at it rather than while editing it.
	- Checked labels sort to the top, so a board with twenty labels never scrolls what's already on the card out of view. The create row is **pinned below the scroller** rather than sitting at its end: it's what you want once the filter has found nothing, and at the end of the list it was two scrolls away. A new label defaults to the first colour the board isn't already using.
	- Enter creates only when nothing matched at all — the rule [[Practice Companion View]]'s quick add settled on after a half-typed query filed a card called `dro`.
	- Chips are tap targets (they open the picker), so they grow under `@media (pointer: coarse)`. The old `≤640px` bump lived in the modal; keying on the pointer instead of the width was needed once the same component started serving the touch-first practice view at every size.
- ## Board chrome
	- **The Board/Practice toggle is one `role="switch"` button, not two tabs.** A press anywhere on the pill — including the half that's already lit, and the padding between the halves — flips it. As a tablist, tapping the lit half did nothing, which on a 32px-tall control reads as a missed tap rather than a no-op. The two halves are inert `<span class="mode-half">`s carrying only the label and the active state.
	- **View mode (`Board` / `Practice`) is persisted per board** as `practice-view-mode:{boardId}`, matching the `practice-session:{boardId}` key convention — a reload mid-practice used to drop you onto the Kanban board, the one place you weren't working. `setViewMode` also force-closes the add drawer and Session Review, which otherwise sat full-screen over a rendered board.
	- **Invite code, export, import, the signed-in address and Sign out all live in the `⋯` menu.** They used to occupy permanent bar space for actions used about once a month, and they were what squeezed the board name to `Tes…`. The measured caveat from commit `4d54734`: at 386 px the name still only gets 62 px, because the invite chrome was already hidden under the ≤760 px media query — the declutter is a desktop win, and the mode switch is now the space-eater.
	- **In-board import replaces the board's contents in place**, keeping its id and `invite_code` so sharing survives — as opposed to the board-list import in `BoardSelectView.vue`, which always creates a new board. Guarded by a `window.confirm` naming the file and the board.
	- **Search filters card names board-wide** (12 results, each labelled with its column) and opens the existing `CardModal`. `Enter` used to fire on a hardcoded `searchResults[0]`, so arrowing down and pressing Enter opened a card you weren't looking at. The highlight now carries an ember inset ring so it outranks a stale `:hover` the pointer left behind when the hands moved to the keyboard. The same keyboard model was ported to the add drawer's search in [[Practice Companion View]].
	- Search and text inputs are forced to 16 px under 760 px: below that iOS Safari zooms the page on focus.
- ## Board select and joining
	- `BoardSelectView.vue` lists boards via a `board_members!inner` join, so RLS and the query agree on what "your boards" means (see [[Supabase]]).
	- **Creating a board is two writes, not one** — `insertBoardWithMembership` inserts the board then the `board_members` row, because a board with no membership row is invisible to its own creator under RLS. There is no transaction: a failed second insert leaves an orphaned board.
	- **Joining goes through the `join_board(uuid)` RPC, not a direct insert.** The `board_members` INSERT policy deliberately doesn't let you add yourself to an arbitrary board; the function is `SECURITY DEFINER` with `search_path = ''`, and `auth.uid()` inside it still resolves to the caller, so the only row you can create is your own membership. `on conflict do nothing` makes re-joining a no-op.
	- **Deleting a board sits behind a per-row `⋯` menu**, mirroring the card modal's `Delete card` (see [[Card Notes]]) — a permanent Delete button next to every board name is one mis-tap from destroying all its columns and cards. Still `window.confirm`-guarded, so it's two deliberate taps. The row can't use `overflow: hidden` any more or it clips the menu; the name button rounds its own left corners instead.
	- The version string in this view's header (`__APP_VERSION__`, defined in `vite.config.ts` from `package.json`) is the project's build marker and is bumped on every push by convention.
- ## Toasts
	- One global stack (`toastStore.ts` + `ToastStack.vue`) replaced a per-store `error.value` that most callers never rendered. Errors hold 10 s and are manually dismissible; successes 4 s.
	- **The raw failure string is demoted to `detail` under a fixed headline** ("That didn't go through"). Every caller passes Supabase's `err.message`, which names what the API thinks broke, not what the user just lost.
	- `role="status"` sits on the always-mounted wrapper — a live region has to exist before its content arrives to be announced. Polite even for errors: nothing here is time-critical and interrupting mid-word while a card name is being typed costs more than it buys.
