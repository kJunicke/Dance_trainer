- The `description` field on a card — freeform markdown, the main way practice history accumulates over months. One column in the DB (see [[Tables]]), rendered on three surfaces with deliberately different treatments.
- ## Render pipeline
	- `src/lib/markdown.ts` is the single place `marked` and `DOMPurify` are used. Everything goes `marked.parse(source, { breaks: true })` → `DOMPurify.sanitize()` → `v-html`.
	- `breaks: true` means a single newline becomes `<br>` — notes get typed as loose lines mid-practice, not as prose paragraphs, so requiring a blank line between every line would be wrong.
	- Two exported renderers: `renderMarkdown()` (plain) and `renderMarkdownWithLinkChips()` (adds `.md-link-chip` + `target="_blank"` + `rel="noopener noreferrer"` to every `<a>`).
	- There is deliberately **no** shared markdown stylesheet or `MarkdownRenderer` component. Each surface writes its own `:deep()` rules, because the three surfaces want genuinely different type sizes and palettes — a shared component would need props for all of it and earn nothing.
- ## The three surfaces
	- ### Board card face (`TaskCard.vue`)
		- Truncated preview: 12px, `--color-ink-dim`, clamped to `max-height: 4.5em`. It's a scanning aid, not a reading surface.
		- Links are **not clickable** here (`pointer-events: none`, inherit color, no underline). On the board face a link is preview text, not a target — a click anywhere on the card should open the card, never navigate away mid-scan.
	- ### Card modal (`CardModal.vue`) — the primary editing surface
		- Preview: 14px/1.5, capped at `max-height: 280px` with its own internal scrollbar, so a description grown over months can't push the destructive `Delete card` button far down the modal. A hairline `border-bottom` on `.desc-field` separates freeform content from that delete action.
		- Uses `renderMarkdownWithLinkChips()`, with chip text in `--color-ember` — ***not*** `--color-ember-light`, which is a hover/fill-only color and an established contrast trap as text on the light theme.
			- **Correction (2026-07-21): that was half right and reached the wrong conclusion.** `--color-ember` is itself only **3.30:1** as 10px text on white, so the decision picked the less-bad of two *failing* options and recorded it as solved. Resolved 2026-07-21: `--color-ember-text` `#a04c00` (5.01 on surface, 5.95 on white) now exists and the chip uses it; `--color-ember` is fills and borders only. The chip's own tint also had to drop 18% → 10% ember, because ember-text on the 18% fill is still only 4.17:1.
		- The preview's base colour is `--color-ink`, with `.placeholder` as the single dim exception. It was the other way round until 2026-07-21 — base dim, with `p`/`ul`/`ol`/`h1-3` overridden back — which meant blockquotes, tables, `<pre>` and bare text nodes silently inherited a 3.92:1 colour. Exceptions are opted into, never out of. See [[UX Backlog]].
		- Bespoke `:deep()` rules for `h1`/`h2`/`h3` (16/15/14px, `--font-display` 700 — field content, not page headings), inline `code` (mono on a `color-mix` ink tint), and the link chip.
	- ### Practice Companion (`PracticeFocusCard.vue`)
		- Separate dark `--pc-*` palette, its own tuned type. See [[Practice Companion View]]. Not a shared component with the modal — same data, different job.
- ## Editing model (card modal)
	- Click the rendered preview → it swaps to a textarea. There is no separate edit button, and no formatting toolbar or markdown cheat-sheet (single-user tool; the `Markdown supported` placeholder is the only hint needed).
	- ### Entering edit mode must not move the text under the pointer
		- **Height is preserved.** The textarea adopts the height the preview just had (`offsetHeight` transfers directly — `* { box-sizing: border-box }` is global in `App.vue`). Without this, a full 280px preview collapsed to the textarea's 180px floor and the user lost their place. Only applied when the measurement *exceeds* the 180px floor, or a short/empty description would inline a min-height below the CSS one and shrink the writing surface.
		- **The caret lands on the word you clicked.** `caretOffsetFromClick(body, event, source)` in `markdown.ts` is the single entry point, shared verbatim with [[Practice Companion View]] — the two surfaces differ only in how they reach their `.md-body`. Three steps: `caretPositionFromPoint()` for the exact text node + offset under the pointer (falling back to `caretRangeFromPoint()`, the older Blink spelling); walk up to the top-level block to get its lexer index; then match that block's rendered prefix against its raw source.
		- **Block index comes from the lexer, not from splitting on blank lines.** A run of headings with no blank line between them is *one* blank-line chunk but *three* rendered elements, which silently desyncs the mapping. `space` tokens carry source length but render to nothing, so they advance the offset without consuming a block index.
	- **Rendered-to-source matching is a greedy walk that ignores whitespace on both sides.** Markup the reader never sees (`**`, `# `, `- `, a link's `](url)`) is stepped over because it doesn't match the next visible character. Whitespace can't be compared directly: `breaks: true` turns a source newline into a `<br>` contributing no text, and marked's own pretty-printing inserts newlines between `<li>`s that were never in the source — matching those desyncs the walk on the first list.
		- The walk never backtracks, so a markup character that happens to equal the next visible one can consume it early and land the caret a character or two off *inside the right word*. Accepted deliberately: that miss is far smaller than the block-start approximation it replaced.
	- **Clicks that miss text still land nearby.** A tap in the gap between two blocks resolves to the end of the *preceding* block, because `caretPositionFromPoint` snaps to the nearest position. Only a click that resolves outside `.md-body` entirely falls back to end-of-source. Until 2026-07-21 every such miss — including the common one of tapping the leading between two paragraphs — jumped to the end of the note, which is what made the field feel like it "always jumps to the end".
		- The `v-html` container carries `.md-body` purely so the click handler can identify which top-level child was clicked.
	- ### Saving
		- Blur on the textarea saves. So does the explicit `Save` button, and so does any modal-close path (X / backdrop / Escape / phone back-gesture) via `closeModal()`.
		- **There is no Cancel button**, and re-adding one would be a lie: clicking Cancel blurs the textarea first, so the blur-save would fire and commit the draft before Cancel could discard it. Discarding would require suppressing the save based on where focus is heading — not worth the moving parts for a personal tool where the risk is a lost edit, not an unwanted one.
		- `saveDescription()` defers collapsing the textarea by a tick (`setTimeout(..., 0)`). Blur fires as soon as the click lands on the *next* element; collapsing synchronously would shift that element out from under the pointer before its own click completed, silently swallowing the tap. Same reasoning and same fix as `PracticeFocusCard.vue`.
		- Persistence is `store.updateCardDescription` → `updateCardField`: optimistic local write, then Supabase, rolling back with a toast on error. No debounce — every save is one immediate request.
