- The `description` field on a card — freeform markdown, the main way practice history accumulates over months. One column in the DB (see [[Tables]]), rendered on three surfaces with deliberately different treatments.
- ## Render pipeline
	- `src/lib/markdown.ts` is the single place `marked` and `DOMPurify` are used. Everything goes `marked.parse(source, { breaks: true })` → `DOMPurify.sanitize()` → `v-html`.
	- `breaks: true` means a single newline becomes `<br>` — notes get typed as loose lines mid-practice, not as prose paragraphs, so requiring a blank line between every line would be wrong.
	- Two exported renderers: `renderMarkdown()` (plain) and `renderMarkdownWithLinkChips()` (adds `.md-link-chip` + `target="_blank"` + `rel="noopener noreferrer"` to every `<a>`).
	- There is deliberately **no** shared markdown stylesheet or `MarkdownRenderer` component. Each surface writes its own `:deep()` rules, because the three surfaces want genuinely different type sizes and palettes — a shared component would need props for all of it and earn nothing.
- ## The three surfaces
	- ### Board card face (`TaskCard.vue`)
		- Truncated preview: 12px, `--color-ink-dim`, clamped to `max-height: 4.5em`. It's a scanning aid, not a reading surface.
		- Links are **not clickable** here (`pointer-events: none`, inherit color, no underline). On the board face a link is preview text, not a target — a click anywhere on the card should open the card, never navigate away mid-scan.
	- ### Card modal (`CardModal.vue`) — the primary editing surface
		- The modal is `max-width: 720px` on desktop (was 560px until 2026-07-22 — it floated as a narrow column with huge side margins), and the preview cap lifts to `440px` at `≥641px`; the phone sheet keeps the tighter 280px. Rationale: the notes field is where the work happens, so it should use the desktop's spare width and height rather than leaving it empty. Editing happens inside that same scroll container — see the per-block editing model below — so the height applies to reading and writing alike.
		- Preview: 14px/1.5, capped at `max-height: 280px` (440px on desktop) with its own internal scrollbar, so a description grown over months can't push the destructive `Delete card` button far down the modal. A hairline `border-bottom` on `.desc-field` separates freeform content from that delete action.
		- Uses `renderMarkdownWithLinkChips()`, with chip text in `--color-ember` — ***not*** `--color-ember-light`, which is a hover/fill-only color and an established contrast trap as text on the light theme.
			- **Correction (2026-07-21): that was half right and reached the wrong conclusion.** `--color-ember` is itself only **3.30:1** as 10px text on white, so the decision picked the less-bad of two *failing* options and recorded it as solved. Resolved 2026-07-21: `--color-ember-text` `#a04c00` (5.01 on surface, 5.95 on white) now exists and the chip uses it; `--color-ember` is fills and borders only. The chip's own tint also had to drop 18% → 10% ember, because ember-text on the 18% fill is still only 4.17:1.
		- The preview's base colour is `--color-ink`, with `.placeholder` as the single dim exception. It was the other way round until 2026-07-21 — base dim, with `p`/`ul`/`ol`/`h1-3` overridden back — which meant blockquotes, tables, `<pre>` and bare text nodes silently inherited a 3.92:1 colour. Exceptions are opted into, never out of. See [[UX Backlog]].
		- Bespoke `:deep()` rules for `h1`/`h2`/`h3` (16/15/14px, `--font-display` 700 — field content, not page headings), inline `code` (mono on a `color-mix` ink tint), and the link chip.
	- ### Practice Companion (`PracticeFocusCard.vue`)
		- Separate dark `--pc-*` palette, its own tuned type. See [[Practice Companion View]]. Not a shared component with the modal — same data, different job.
- ## Editing model (card modal) — per-block inline edit
	- **Prototype, branch `inline-block-edit` (2026-07-25).** Replaces the whole-field mode swap in the card modal only; [[Practice Companion View]] still swaps its entire field.
	- **The problem it solves.** The old model swapped the *entire* rendered note for one raw textarea. On a note the size of the Drops card — headings, nested lists, a dozen link chips — every small edit blanked the whole reading surface into `##`/`- `/`[](…)` and cost a few seconds of re-orientation before you could find the line you meant to change. Adding SM2-style complexity elsewhere was declined for the same reason: the annoyance was never the markdown, it was losing your place.
	- **Only the clicked block becomes editable.** `MarkdownNote.vue` renders the note as a list of top-level blocks (`splitBlocks()` in `markdown.ts`); clicking one swaps *that block* for a textarea while every other block stays rendered. The surrounding note never changes, so there is nothing to re-orient to.
	- **Granularity is the lexer's, not the line's.** One `marked` token = one editable block. A whole bullet list is a single token, so clicking any bullet opens the entire list's raw source. Accepted for the prototype: the headings and paragraphs around it still hold their rendered shape, which is where the orientation came from. Splitting `list_item`s into separately-editable blocks is the obvious next step if it grates.
	- **Blocks are rendered individually.** `splitBlocks()` runs `renderMarkdownWithLinkChips()` per token rather than rendering the note once and slicing the DOM. Consequence: a block can't reference a link definition declared in another block. Not a pattern these notes use.
	- ### Entering edit mode must not move the text under the pointer
		- **The editor never scrolls internally.** `autosize()` sets its height to `scrollHeight` on open and on every keystroke, so it grows to fit and pushes the blocks below it down (`overflow: hidden; resize: none`). Raw markdown is almost always taller than what it renders to — `##`, `- `, and a link's `](url)` all add wrapped lines — so an editor pinned to the rendered block's height hid most of what you were editing behind a scrollbar, which is the same lost-your-place problem the model exists to remove. The block's rendered `offsetHeight` stays as a `min-height` floor so short raw doesn't jump the layout upward.
		- **A block's `raw` does *not* carry the blank line after it.** marked keeps the blank lines *between* blocks in their own `space` tokens, so a token's `raw` usually stops at its last character. The first version of this assumed the opposite and re-added a `\n\n` on every save, stacking another blank line into the gap each time — the Drops note had grown runs of ten-plus newlines before it was caught. `blockSeparator()` now prefers whatever separator is already there.
			- The exception is a block glued directly to the next one with a single `\n` (a heading with content on the following line, which is how Confluence exports land). There `raw` *does* end in `\n`, and it has to be preserved or a no-op edit changes the file.
			- But a single `\n` ends a heading or a list and *not* a paragraph, so rewriting `### Head` into plain text would swallow the line below into the same block. `blockSeparator()` re-lexes the spliced result and bumps to `\n\n` if the first token would run past the block — asking the lexer rather than keeping a list of which constructs self-terminate.
		- **Opening is handled on `mousedown`, and it must `preventDefault()`.** Two separate reasons, both learned the hard way:
			- Committing the open editor reflows the note — the raw block collapses back to its rendered height — and that reflow lands *between* mousedown and click. A `click` handler therefore ran against a layout where the block being aimed at had already slid out from under the pointer, so the tap hit the wrong block or nothing at all. Resolving on mousedown reads the layout as it still stands.
			- Vue flushes `nextTick` at the microtask checkpoint *before* mousedown's default action runs. So without `preventDefault()` the editor mounts and gets focused, and the browser then moves focus to the modal backdrop — firing blur, which saves and closes the editor in the same gesture that opened it. The editor appeared not to open at all.
			- The click is carried across the reflow as the target block's **start offset** plus a caret offset within it — not as a pixel coordinate or a block index, both of which go stale when the note reflows. `openAt()` matches on that start offset, falling back to whichever block now covers it if the save re-lexed the text around it.
			- **Match on the block's start, not on "the block containing this offset".** The first version resolved the target by asking which block contained the absolute caret offset, and a caret at the very end of a block is also the first offset of the next one — so clicking a block's last word, or anywhere in the slack to the right of a short line (where `caretPositionFromPoint` returns end-of-block), opened the block *below*. This was true of every block in the note, not an edge case.
		- **The caret lands on the word you clicked.** `caretOffsetInBlock(blockEl, event, raw)` — the block-scoped twin of `caretOffsetFromClick()`, which [[Practice Companion View]] still uses. The caller already knows which block was hit, so there's no lexer index to resolve; both funnel into the same `offsetInRaw()` walk described below. `caretPositionFromPoint()` gives the exact text node + offset under the pointer (falling back to `caretRangeFromPoint()`, the older Blink spelling).
		- **Block index comes from the lexer, not from splitting on blank lines.** A run of headings with no blank line between them is *one* blank-line chunk but *three* rendered elements, which silently desyncs the mapping. `space` tokens carry source length but render to nothing, so they advance the offset without consuming a block index.
	- **Rendered-to-source matching is a greedy walk that ignores whitespace on both sides.** Markup the reader never sees (`**`, `# `, `- `, a link's `](url)`) is stepped over because it doesn't match the next visible character. Whitespace can't be compared directly: `breaks: true` turns a source newline into a `<br>` contributing no text, and marked's own pretty-printing inserts newlines between `<li>`s that were never in the source — matching those desyncs the walk on the first list.
		- The walk never backtracks, so a markup character that happens to equal the next visible one can consume it early and land the caret a character or two off *inside the right word*. Accepted deliberately: that miss is far smaller than the block-start approximation it replaced.
	- **Clicks that miss text still land nearby.** A tap in the gap between two blocks resolves to the end of the *preceding* block, because `caretPositionFromPoint` snaps to the nearest position. Only a click that resolves outside `.md-body` entirely falls back to end-of-source. Until 2026-07-21 every such miss — including the common one of tapping the leading between two paragraphs — jumped to the end of the note, which is what made the field feel like it "always jumps to the end".
		- The `v-html` container carries `.md-body` purely so the click handler can identify which top-level child was clicked.
	- **Placing the caret is not enough — it must also be scrolled into view.** `focusAtOffset(el, offset)` in `markdown.ts` is the shared focus entry point both surfaces now call: focus with `preventScroll` (so the browser doesn't scroll the modal to reach the field, which yanked the outer sheet to its bottom on short windows), then `setSelectionRange`, then `scrollCaretIntoView`. That last step is the non-obvious one: Blink's `setSelectionRange` places the caret but *never* scrolls it into view, and Vue's `v-model` parks a freshly-mounted textarea scrolled to its *end*. So until 2026-07-22, clicking near the top of a long note opened the editor showing the note's *bottom* with the caret stranded off-screen above — the correct caret position was useless because you couldn't see it. `scrollCaretIntoView` measures the caret's Y with an off-screen mirror `<div>` that wraps text exactly as the textarea does (same content width, font metrics, `tab-size` — the note editor inserts real tabs), then sets `scrollTop` to centre that line.
	- ### Saving
		- Blur saves. So does `Cmd`/`Ctrl+Enter`, and so does any modal-close path (X / backdrop / Escape / phone back-gesture) — `closeModal()` calls the component's exposed `flush()`.
		- `Escape` cancels the block edit and **stops propagating**. Without `stopPropagation()` it kept bubbling to the modal's own keydown handler and closed the whole card, which is not what backing out of one paragraph should do.
		- The `Save` button is gone — with one block open at a time, blur and `Cmd+Enter` cover it, and a button pinned under a growing editor was just another thing moving around.
		- **Saving splices, it doesn't rewrite.** `source.slice(0, start) + draft + source.slice(start + raw.length)`, using the `start`/`raw` the lexer already gave the block. Everything outside the edited block is byte-identical, so no round-trip through a renderer can quietly reformat the rest of a note.
		- **A block emptied of visible content is deleted, not kept as a blank row.** `hasVisibleContent()` ignores zero-width and non-breaking characters, which `trim()` does not: notes pasted out of Confluence contain lone `U+200C` paragraphs that render as nothing but survive every emptiness check, so they showed up as blank blocks that couldn't be deleted (backspacing them looked like it did nothing). `splitBlocks()` treats such a token like a `space` token and skips it, so it never renders as a block — the character stays in the source, where it was already invisible.
		- **Editing is the whole story; appending is a footnote.** A `+ add` row at the end opens an empty trailing block, inserting the `\n\n` separator if the note doesn't already end with one. New notes are mostly *appended* elsewhere (Practice Companion); in the modal the job is fixing lines that already exist.
		- Persistence is `store.updateCardDescription` → `updateCardField`: optimistic local write, then Supabase, rolling back with a toast on error. No debounce — every save is one immediate request.
