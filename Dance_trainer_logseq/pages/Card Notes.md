- The `description` field on a card — freeform markdown, the main way practice history accumulates over months. One column in the DB (see [[Tables]]), rendered on three surfaces through one shared component (`MarkdownNote.vue`), each theming it differently via CSS custom properties.
- ## Render pipeline
	- `src/lib/markdown.ts` is the single place `marked` and `DOMPurify` are used. Everything goes `marked.parse(source, { breaks: true })` → `DOMPurify.sanitize()` → `v-html`.
	- `breaks: true` means a single newline becomes `<br>` — notes get typed as loose lines mid-practice, not as prose paragraphs, so requiring a blank line between every line would be wrong.
	- Two exported renderers: `renderMarkdown()` (plain, `href`/`target`/`rel` stripped — used read-only) and `renderMarkdownWithLinkChips()` (adds `.md-link-chip` + `target="_blank"` + `rel="noopener noreferrer"` to every `<a>` — used per-block wherever the note is edited).
	- **Correction (2026-07-26): reversed.** This page used to say there was deliberately no shared markdown stylesheet or `MarkdownRenderer` component, because the three surfaces' different type sizes and palettes would need a props explosion to cover and would earn nothing. That reasoning didn't hold up: the sizes and palettes are *values*, not structure, and CSS custom properties carry values across a component boundary for free — no props needed for any of it. `MarkdownNote.vue` (below) is now that shared component. The clearest evidence the reversal points at is the caret-jump fix below, which had to be ported to [[Practice Companion View]] a second time by hand before it was made properly shared. The heading-size rule is a related but smaller case: `assets/tokens.css` already held **one** global block keyed off all three surfaces' class names (`.task-description`, `.desc-preview`, `.note-preview`) — its own comment records that it was written specifically to stop an *earlier* round of three per-surface copies drifting apart, so a shared rule already existed here, just as global CSS rather than as part of a component. This pass took that global block out of `tokens.css` entirely and moved it into `MarkdownNote.vue`'s own scoped styles — one less global selector reaching into three unrelated components' markup, and heading rules now live where the component that owns them lives. (This page previously also claimed `CardModal.vue` carried its own bespoke `:deep(h1/h2/h3)` rule at fixed 16/15/14px — that was already stale before this pass; the code at HEAD had no such rule, only the one shared `tokens.css` block. Corrected here, not carried forward.)
- ## `MarkdownNote.vue` — the shared component
	- Promoted 2026-07-26 from a card-modal-only prototype (see "Editing model" below — still branch `inline-block-edit`) to the single component all three surfaces render `description` through. `TaskCard.vue` ([[Board View]]) and `PracticeFocusCard.vue` ([[Practice Companion View]]) both switched to it in the same pass; see those pages for what changed on their side.
	- **API.** Props `source: string`, `editable?: boolean` (default `true`), `placeholder?: string`. Emits `update:source`. Exposes `flush()` — the parent's hook to commit an open block edit before the component goes away: `CardModal`'s close path and `PracticeFocusCard`'s `onBeforeUnmount` both call it.
	- **Theming.** `MarkdownNote` is a single-root component, so a class a parent puts on `<MarkdownNote class="...">` lands on its actual root element and the parent's own scoped styles still reach it (see the comment on `.task-description` in `TaskCard.vue`). Parents theme it by setting `--note-*` custom properties on that host class rather than passing style props. The variables and the component's own fallback (what a host gets for free if it sets nothing):
		- `--note-font-size` (14px)
		- `--note-ink` (`#2a2420`), `--note-ink-dim` (`#6a6156`)
		- `--note-accent` (`#a04c00`), `--note-accent-bg` (`rgba(224, 109, 10, 0.1)`) — link-chip text and fill
		- `--note-hover-bg` (`#ffffff`) — block hover highlight, editable mode only
		- `--note-editor-bg` (`#e6e0d4`), `--note-editor-border` (`#e06d0a`) — the open block textarea and the formatting bar
		- `--note-chip-max` (`40vw`) — link-chip max-width, for the head-truncation below
		- `--note-block-gap` (`8px`) — space after a paragraph/list; the board face tightens this to 4px (see [[Board View]])
		- `--note-heading-scale` (`1`) — how much of the heading step above the base survives; the board face sets `0` (see the heading block below)
	- **Read-only mode (`editable: false`) is the board card face.** `TaskCard` renders one of these per card for a whole board, so it takes a cheaper path on purpose: one `renderMarkdown()` parse of the whole note into one `.md-block`, no `splitBlocks()` lexing per token, no pointer/blur handlers at all. The template reads exactly one of two lazy computeds depending on `editable`, so the block machinery costs nothing when it isn't rendered.
	- **The global heading block moved out of `assets/tokens.css` and into this component**, as `:is(h1, h2, h3, h4, h5, h6)` scoped inside `.md-block :deep()`. Same em-relative sizing as before (h1 1.15em, h2 1.08em, h3-6 1em) for the same reason as before: the three hosts read at different base sizes (board 12px, modal and practice card 14px), so each host keeps owning its own base and only the *relative* scale is shared.
		- **How much of that scale applies is the host's call, via `--note-heading-scale`.** It multiplies the *step above the base*, not the whole size — h1 is `calc(1em + 0.15em * var(--note-heading-scale, 1))`, h2 `calc(1em + 0.08em * …)` — so `1` (the default, what the modal and the practice card use) is the sizing above unchanged, and `0` collapses every level onto the host's own base. Scaling the whole em value instead would need a different factor per level to land them all on the base, and any factor low enough to flatten h1 would push h2 *below* body text.
		- **The board face sets `0`, because the card title has to be the largest thing on the card.** At full scale an in-note `# H1` renders 13.8px against the 15px `.task-title` — smaller by measure, but at weight 700 against the title's 600 and in the same face, so it read as the heavier of the two and competed for the eye while scanning a column. Flattened, a heading is still marked by weight and by ink, and size is left to say one thing only: this is the card's name. The other two surfaces already satisfy the rule and keep the full scale — the modal is a 22px title over a 14px base (h1 16.1px), the practice focus card 20px over 14px. **Rejected: raising `.task-title` instead** — the same fix pointed the other way, but it costs column density on a phone, where the point of the face is how many cards fit above the fold.
- ## The three surfaces
	- ### Board card face (`TaskCard.vue`)
		- Renders `<MarkdownNote :editable="false">`, themed `--note-font-size: 12px`, `--note-ink: var(--color-ink-dim)`, `--note-heading-scale: 0` (headings flat at 12px, so the 15px title stays the largest thing on the card — see the heading bullet above), `--note-block-gap: 4px` (tighter than the 8px default — at 8px a three-paragraph note spent half a line of the 4.5em clamp on gaps instead of text). The clamp itself (`max-height: 4.5em`, `overflow: hidden`) still lives on `.task-description` in `TaskCard.vue`, unchanged. It's a scanning aid, not a reading surface.
		- Links are inert twice over: `renderMarkdown()` strips `href`/`target`/`rel` outright (a click anywhere on a board card should open the card, never navigate away mid-scan — invisible anchors were also sitting in the tab order before this), and `TaskCard.vue` additionally sets `pointer-events: none` on any that render.
	- ### Card modal (`CardModal.vue`) — the primary editing surface
		- The modal is `max-width: 720px` on desktop (was 560px until 2026-07-22). **No height cap or internal scroll on the notes field any more.** Until 2026-07-26 the preview capped at `280px`/`440px` with its own scrollbar, so a description grown over months couldn't push the destructive `Delete card` button out of reach below it. `Delete card` moved into a `⋯` overflow menu next to the close button (see below), which removed the reason for the cap: the notes field now grows to its natural height and the modal/backdrop (or the phone's full-screen sheet) does all the scrolling, for reading and writing alike.
		- Themed `--note-ink: var(--color-ink)` (full ink; `.placeholder`/`+ add` dim tone is the one opted-in exception, never the default — blockquotes, tables and bare text nodes inherit full ink), `--note-accent: var(--color-ember-text)`, `--note-accent-bg: color-mix(in srgb, var(--color-ember) 10%, transparent)`, `--note-editor-bg: var(--color-bg)`, `--note-editor-border: var(--color-ember)`.
			- **Chip contrast, still the load-bearing reason it's `--color-ember-text` and not `--color-ember` or `--color-ember-light`.** `--color-ember-light` is a hover/fill-only color; `--color-ember` is itself only **3.30:1** as 10px text on white — picking it over ember-light was the less-bad of two *failing* options, recorded as solved on 2026-07-21 when it wasn't. `--color-ember-text` `#a04c00` (5.01 on surface, 5.95 on white) is the one that actually clears the floor. The chip's own tint is 10% ember, not 18%: ember-text on the 18% fill is still only 4.17:1, the lighter tint clears 4.52:1.
		- **On phones the modal is a full-screen sheet that sizes to its content, and the backdrop scrolls it.** The backdrop must stay `align-items: flex-start` there. It was `stretch`, which sizes the sheet to the backdrop's own height — one viewport — so any card taller than the screen painted its surface for the first `100dvh` only and the rest of the content scrolled over the bare dark backdrop. `min-height: 100dvh` cannot rescue that: it equals the stretched height, so nothing grows. The `min-height` is still what keeps a *short* card full-screen. Found once the family tree started pushing cards past a screen ([[Card Relationships]]), but it applies to any long note.
		- `Delete card` lives behind a `⋯` button beside the close button — two deliberate taps instead of one always-visible destructive button in the body. Escape closes the menu first and the modal only on a second press; a document click outside `.modal-actions` closes it the same way the label-adder popover already did. The menu is anchored to the actions row's **right** edge so it grows leftward into the modal — anchoring left instead grew it rightward off the phone sheet's edge, clipped by the backdrop's overflow, leaving no way to reach Delete on a phone at all (caught before shipping; see the bug list below).
	- ### Practice Companion (`PracticeFocusCard.vue`)
		- **Correction (2026-07-26):** this used to say "not a shared component with the modal — same data, different job." That's now false: `PracticeFocusCard` renders `<MarkdownNote>` too, its own bespoke editor deleted outright. See [[Practice Companion View]] for what that removed. - ## Editing model — per-block inline edit
	- **Branch `inline-block-edit`.** Prototyped 2026-07-25 for the card modal only; promoted 2026-07-26 to back every editable surface (card modal + [[Practice Companion View]]'s focus card) through `MarkdownNote.vue`. The Companion's own bespoke editor — a full-height textarea filling the card, with its own click-to-caret and blur-save logic — is gone; that page no longer swaps its whole field either.
	- **The problem it solves.** The old model swapped the *entire* rendered note for one raw textarea. On a note the size of the Drops card — headings, nested lists, a dozen link chips — every small edit blanked the whole reading surface into `##`/`- `/`[](…)` and cost a few seconds of re-orientation before you could find the line you meant to change. Adding SM2-style complexity elsewhere was declined for the same reason: the annoyance was never the markdown, it was losing your place.
	- **Rejected: Obsidian-style live preview** (CodeMirror 6 with decoration-based hiding of the markup, so the raw source is styled in place rather than swapped out). Estimated ~1–2 weeks, and it is *weakest exactly where this app is used* — touch. It was also solving the wrong complaint: the annoyance was never seeing `**` markers, it was losing your place when the whole field swapped. Per-block editing solves that directly, for a fraction of the work. Don't re-propose a CodeMirror rewrite without a reason that isn't "raw markers are ugly".
	- **Only the clicked block becomes editable.** `MarkdownNote.vue` renders the note as a list of top-level blocks (`splitBlocks()` in `markdown.ts`); tapping one swaps *that block* for a textarea while every other block stays rendered. The surrounding note never changes, so there is nothing to re-orient to.
	- **Granularity is the lexer's, not the line's.** One `marked` token = one editable block. A whole bullet list is a single token, so clicking any bullet opens the entire list's raw source. Shipped that way deliberately, to see whether it grates before splitting `list_item`s into separate blocks — see [[Open Work]], unchanged by this pass.
	- **Adjacent same-marker lists merge into one block, and this is accepted, not a bug.** Rewriting a block into `- foo` beside an existing bullet list joins that list: CommonMark dropped the old "a blank line ends a list" rule, so 1, 2, 5 or 10 blank lines between them all still lex as one list token, and `blockSeparator()` has no separator it can return that would keep them apart. No bytes are lost — the note still renders correctly — what's lost is the block *boundary*, so the merged list opens as one editor from then on. **Rejected: injecting an `<!-- -->` comment**, the one construct that does separate two lists in CommonMark. It would write permanent noise into notes that are kept for years, to fix a case where nothing is actually lost. `blockSeparator()` also only ever inspects what *follows* a block, so the mirror case — rewriting a block into a bullet with a list *above* it — isn't even detected; same accepted outcome.
	- **Blocks are rendered individually.** `splitBlocks()` runs `renderMarkdownWithLinkChips()` per token rather than rendering the note once and slicing the DOM. Consequence: a block can't reference a link definition declared in another block. Not a pattern these notes use.
	- ### Opening a block: capture on `pointerdown`, commit on `pointerup`
		- **This replaced the old `mousedown`-only gesture**, which had a real cost on touch: a scroll gesture that happened to start on top of a block opened an editor. Both halves of the new gesture have to exist. Resolving the target on **down** is what survives the reflow — committing the previously-open editor collapses its raw block back to rendered height, and that reflow lands before any later event, so a handler running on up/click would aim at a layout where the target block had already slid out from under the pointer. Acting only on **up** is what lets a scroll that starts on a block stay a scroll: if the pointer moves more than 10px (`MOVE_CANCEL_PX`) before release, the pending open is discarded.
		- What's carried from down to up is the target block's **start offset** plus a caret offset within it — never a pixel coordinate or a block index, both of which go stale when the note reflows.
		- **A separate root `mousedown` handler still exists, purely to `preventDefault()` the browser's default focus change.** This is not redundant with the pointerdown/pointerup gesture above, and the reason is a Chrome/touch-specific quirk worth keeping on this page: on touch, Chrome fires the `pointerdown` **non-cancelable** while a scroll is still possible (it doesn't yet know whether this gesture will become a scroll), so `preventDefault()` on `pointerdown` is not an option there. And the *compatibility* `mousedown` synthesized for touch fires **after** `pointerup` — i.e. after the editor has already opened and focused. Without a `preventDefault()` somewhere in that window, the browser then moves focus off the freshly-mounted textarea (Vue flushes `nextTick` at the microtask checkpoint before the default focus action runs), firing blur, which saves and closes the editor in the same gesture that opened it — it looked like it never opened at all. The one `mousedown` handler covers both the real mouse event and the touch compatibility one; it's the only place `preventDefault()` is used, and it exempts `a` and the open `textarea` (both need to stay interactive) but deliberately *not* buttons — see the formatting bar below for why that exemption would be fatal there.
		- **Link chips still opt out of edit-on-click entirely**, now via `(e.target as HTMLElement).closest('a')` inside the pointerdown handler rather than a preventDefault escape. Following a reference video is the commonest thing done in these notes. A block that is nothing but a chip stays editable from the slack beside it — chips cap at `--note-chip-max`, so most of the row is empty and the hover highlight covers the whole width.
		- **Block index still resolves from the lexer** (`space` tokens advance the offset without consuming a block index) and **matching is still on the block's start offset**, not "the block containing this offset" — a caret at a block's very end is also the first offset of the next one, so matching on containment opened the wrong block at every boundary. Both unchanged from the original design.
	- ### Saving, closing, and the sequence counter
		- **Blur commits immediately; the visual close is deferred one macrotask.** Blur fires as the user's tap lands on the *next* element (a Session Review bucket button, say), and collapsing the editor synchronously would shift that element out from under the pointer before its own click completed, silently swallowing the tap. Only the collapse is deferred (`setTimeout(…, 0)`) — the data is written on blur itself, not deferred with it. Every *explicit* close (`Cmd`/`Ctrl+Enter`, switching blocks, `flush()`, append) still commits and closes in the same tick.
		- **A per-open sequence counter (`openSeq`/`committedSeq`) guards the window the defer opens.** Two things need telling apart: the commit, which must fire at most once per open (a second commit inside the deferred window would splice an already-saved draft over a source that has since moved on), and the deferred close itself, which must not close an editor that opened *after* the blur that scheduled it. Both are compared against the sequence number stamped when that editor opened.
		- **Splicing still doesn't rewrite.** `source.slice(0, start) + replacement + source.slice(start + raw.length)` — everything outside the edited block stays byte-identical. `commitEdit()` now returns the length delta the splice produced (0 when nothing changed), which the pointerup handler uses to carry a still-pending offset across an edit that just closed, rather than re-deriving it against a source that has already moved.
		- Escape still cancels the block edit and stops propagating, so it doesn't also close the whole modal. `Cmd`/`Ctrl+Enter` still commits without reaching for the mouse. The `Save` button is still gone.
		- **Enter inside a list item continues the list** — same indentation, same marker, and an ordered marker counts on (`1.` → `2.`; markdown renumbers on render either way, but a raw block full of `1.` is what you're looking at while editing). Enter on an *empty* item clears the marker instead, ending the list: that's the only way out of a list from a phone keyboard, which has neither Tab nor Escape. Anything that isn't a list item — a paragraph, a heading, a selection spanning text — keeps the plain newline, so `continueList()` reports whether it handled the key and only then is the default suppressed. It writes through the same `applyToDraft()` the formatting bar uses, so the editor re-grows in the same step.
		- **A keyboard close hands focus back to whatever had it before the editor opened.** Found in browser testing, and it is a direct consequence of the `preventDefault()` above: the card modal focuses its `.backdrop` on mount precisely so Escape has an element to fire on, and suppressing mousedown's default focus change means clicking a block no longer moves focus there. So after Escape or `Cmd+Enter` closed a block, `document.activeElement` was `<body>` and Escape stopped closing the card at all — you had edited one paragraph and the modal's own keyboard exit was gone. `openAt()` records `document.activeElement` and the two keyboard closes restore it. Deliberately *not* restored on a blur close (the user has already moved focus themselves) or when switching straight to another block (that block's editor is about to take it).
	- ### A formatting bar, coarse pointers only
		- Shown only while a block is open **and** `window.matchMedia('(pointer: coarse)').matches` — desktop has a real Tab key and `Cmd`/`Ctrl+Enter`, and never sees this bar. It exists because a phone keyboard has no Tab key at all, which made nesting a list on mobile impossible: outdent (`⇤`), indent (`⇥`), bullet (`•`), bold, italic, and a heading-cycle (`H` — `#` → `##` → `###` → none on the caret's line).
		- **The bullet button toggles, and a mixed selection bullets rather than strips.** It only strips when *every* line the selection touches is already a list item — dragging across a paragraph and a stray bullet gives you a list, which is the outcome you were asking for. Each line keeps its own leading whitespace, so bulleting inside an indented run stays nested. Ordered items (`1.`, `1)`) count as list items for the strip test, so the button also un-numbers a numbered list.
		- **Pinned above the on-screen keyboard via `visualViewport`.** The layout viewport doesn't shrink when the keyboard opens; the visual viewport does. The bar's `bottom` offset is `window.innerHeight - (vv.height + vv.offsetTop)` — the gap between the two — recomputed on the visual viewport's own `resize`/`scroll` events, subscribed only while the bar is showing.
		- **Every button fires on `pointerdown.prevent`, not `click`.** That keeps focus (and the textarea's selection) on the editor instead of the button, so `applyToDraft()` can write the new text back and restore the selection without ever losing it. It's also why buttons are the one thing the root `mousedown` guard deliberately does *not* exempt: letting a button take focus would blur the textarea, which commits and (a macrotask later) closes the editor — for the formatting bar that's fatal, since the first indent tap would close the very editor it was meant to indent.
	- ### Bugs found and fixed in review (each is a trap worth not re-laying)
		- **`pendingReplacement()`'s two-sided `.trim()` silently ate the leading tab** the indent button (and the Tab key at offset 0) had just inserted — indenting a block, or nesting a list's first bullet, saved a byte-identical source and looked like a no-op. Now trailing-only (`replace(/\s+$/, '')`); the leading side is never trimmed, because nothing else owns it.
		- **Deleting a block left its separator behind.** Splicing out only `raw` (not the blank line after it) meant the stray newline lexed as a `space` token that `splitBlocks()` skips — invisible, but permanent, and it grew by one every deletion. `commitEdit()` now strips a leading run of newlines from what follows when the replacement is empty (i.e. the block is being deleted).
		- **The overflow menu was anchored `left: 0` inside a right-anchored actions row**, opening roughly a third of itself past the modal's right edge on a phone — clipped by the backdrop's overflow, with no path to Delete at all since it no longer lives in the modal body. Caught before shipping; fixed by anchoring the menu to the row's right edge instead (see the card-modal bullet above).
	- ### Dead code removed
		- `focusAtOffset()` dropped `preventScroll` — the editor no longer has an internal scroll to protect (see below), so the browser's own default focus-scrolling is now what brings the field into view; tried as the simpler option first rather than re-solving it by hand.
		- `scrollCaretIntoView()`, `caretOffsetFromClick()`, `blockAt()` and `sourceOffsetAt()` were deleted outright. All four existed only to let [[Practice Companion View]]'s bespoke editor resolve a click into a caret offset and then scroll that caret into view inside its own textarea; now that surface delegates entirely to `MarkdownNote`, nothing calls them.
		- **Be honest about what this leaves unsolved.** The browser's default focus-scroll guarantees the *element* is scrolled into view, not the caret's *line* within it. A block that autosizes taller than the visual viewport can still leave the caret off-screen — or behind the virtual keyboard on a phone. Accepted, not solved; see [[Open Work]].
	- **Verification: no test suite, again.** As with the 2026-07-25 prototype, this pass was checked with a throwaway property script run against a real note rather than a committed test — round-trip/no-op/delete/delta properties, same shape as the original splice verification below, re-run against the new commit/blur/sequence-counter logic. Nothing from this pass is in a test file.
	- **Test the splice logic headlessly against a real note before opening a browser** remains the standing practice here. The properties that matter are invisible on screen: a no-op edit must round-trip byte-identically, twenty consecutive saves must not grow the source, emptying any block must delete exactly that block, and the save delta must predict the next block's new start. Run against the real Drops note, that pass is what first surfaced both the newline-accumulation and the heading-swallowing-the-next-line case — neither of which shows up as anything you'd notice by clicking around.
	- **The caret lands on the word you clicked**, via `caretOffsetInBlock(blockEl, event, raw)` and the shared `offsetInRaw()` walk — unchanged mechanics from the original design; markup the reader never sees (`**`, `# `, `- `, a link's `](url)`) is stepped over because it doesn't match the next visible character, and whitespace is compared loosely for the same `breaks: true` / pretty-printed-`<li>` reasons as before.
- ## The note's headers are also a split seam
	- A note's header structure doubles as the cut line for [[Card Relationships]]: a header plus everything down to the next header of the same or higher level can be lifted out into a child card, and a child folded back in becomes a header plus its note. `noteSections`, `splitSection`, `demoteHeadings` and `mergeNote` in `lib/markdown.ts` are the pure transforms, riding the same `marked` lexer offset walk as `splitBlocks()`.
	- **`noteSections()` returns every heading at every level, so its ranges overlap** — a `##` and the `###`s beneath it are separate entries with nested ranges. It's a flat pick-one menu, never a partition; iterating it and splitting each entry would extract the same text twice.
	- **`MarkdownNote.vue` deliberately does not own the split action.** It's shared by the board face and the practice focus card, and a per-block split button would hand both of them a card-mutating control they must not have. `CardModal` presents the header list instead.
	- Headings inside blockquotes and list items are out of scope for both transforms: they're heading tokens, but they hang off a parent whose `raw` carries the `> `/indent prefix, so their offsets don't map back to the source by summing raw lengths.
	- Demotion **clamps at 6 rather than emitting seven hashes**, which compresses nesting instead of preserving it — two headings that both land past 6 collapse onto 6 and can't be told apart afterwards. Only reachable from notes that already nest five or six deep.
	- Setext headings (`Foo` over `---`) are real heading tokens, so they split normally; on demotion they're rewritten as ATX, because setext can only spell levels 1–2 and demotion routinely needs 3+. A zero-delta demote leaves them alone, so setext survives unless it actually has to move.
	- **Merge appends at the end of the parent note and does not restore the section's original position.** The offset goes stale on the first edit and the parent note is edited constantly — so split→merge round-trips the text, not the ordering.
	- **The split/merge transforms normalise CRLF to LF before doing anything.** `marked.lexer()` converts line endings before tokenising, so on a CRLF note the token `raw` lengths no longer sum to the source length and the offset walk drifts one byte per `\r`. `splitBlocks()` rides the same walk and has the same latent flaw — it has never bitten because nothing in the app authors CRLF, but a Trello import can carry it in and per-block editing splices rather than rewrites, so it persists. See [[Card Relationships]].
	- Verified the standing way: a property script over 13 fixtures including a real note, run before any browser work — split losslessness, seam whitespace, nested subheaders travelling with their section, and fenced code surviving demotion byte-identically.
